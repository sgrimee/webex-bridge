# Mercury event observations — Agents social

Live tests use the user's separate `webex-bridge` integration. The original ten granular OAuth scopes were confirmed in the token response but WDM/Mercury returned HTTP 403. After explicit user approval, the bridge integration requested **`spark:all` only**; WDM returned 200 and Mercury connected. These observations are metadata-only: no message bodies, tokens, codes or raw events were saved.

| Operation | Mercury activity verb | REST hydration | Observation |
|---|---|---|---|
| Human post, no mention | `post` | `GET /messages/{event activity ID}` returns body | Created and received timestamps differed by 1,863 ms in the first test; room and sender matched the test route. |
| Human edit of that message | `post` again (not `update`) | `GET /messages/{new activity ID}` resolves to the **original canonical message ID**, same `created`, a later `updated`, revised body | The event activity ID changed, but the REST message ID did not. The event reached the probe 556 ms after `updated`. Classify semantic edit after hydration by canonical message ID + `updated > created`, not Mercury verb or activity ID. |
| Human delete (threaded reply and later thread starter) | `delete` (also a `leave` room activity near one deletion; do not infer actual room departure) | `GET /messages/{canonical deleted ID}` returns HTTP 404 | Metadata confirmed: `activity.id` is a new delete activity UUID, `target.id` is the room UUID, `target.global_id` is the **ROOM** geo-ID, and `parent` is absent. There is **no message ID** in the parsed delete event. `webex-rust::Event::try_global_id()` mislabels the room as a Message ID; bridge probe now validates it as a Room ID, reports `messageId: null` and `reconcileRoom: true`. Step 2 must reconcile that room against the encrypted mirror, then mark missing canonical IDs deleted and purge bodies. |
| Reply in a thread | `post` | `GET /messages/{activity ID}` returns canonical reply ID and `parentId` equal to thread-start message ID | Probe latency 414 ms; parent association verified. |
| Forced refresh listener gap | N/A: no Mercury listener for 90 s | Rebuilt daemon's dev-room catch-up stored one human post created during the gap | `created=1`, `gaps=0`; validated that forced refresh publishes a disconnection before it rebuilds so catch-up runs on the newly authenticated REST client. |
| Membership cycle | No owner-side Mercury membership activity observed | REST removal and immediate re-invite succeeded; participant remains a member | The owner-side stream received only safe acknowledgement control traffic. This shape must be observed from a participating second bridge during the two-person trial; do not invent a membership mapping. |
| Human post, no mention | `post` | REST hydration returned message metadata with `mentioned_people=0` | Message body was not logged. |
| Human post, named mention | `post` | REST hydration returned message metadata with `mentioned_people=1` | A consented participant was selected through the normal Webex mention autocomplete; neither body nor mentioned person ID was logged. |

Only `Agents social` is allowed for message/membership writes during the development phases. The separate bridge Mercury device name ends in `-webex-bridge` so it does not collide with the existing TUI device. A subsequent probe revision ignores typing/control events without message IDs and emits sanitized ID diagnostics for malformed, unknown and missing-room events. A second unmentioned post was hydrated in 1,126 ms. A thread starter and reply were hydrated in 790 and 414 ms, with the reply's `parentId` matching the starter ID. Probe and REST output contain IDs, timestamps and lengths only; never body text. Do **not** mark a room as left merely because Mercury emitted `leave`: verify membership with REST first.
